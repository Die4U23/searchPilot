# 2026-10-14 搜索候选扫描性能验证

来源：`searchpilot`。同机四轮 **A→B→B→A** 的正式 HTTP 请求为 **1920/1920 成功**。每版本每模式合并 240 请求后，vector / hybrid / LTR 的 p95 分别下降 **47.89% / 43.42% / 25.21%**；但 vector 和 LTR 的 p99 分别上升 **12.02% / 31.86%**。这是吞吐与主要延迟分位数的改善证据，**不是所有尾部改善或 SLA 通过**。

本轮采用只装载搜索的隔离应用，未验收整个默认应用。两次默认应用启动先后阻塞，未被删除；首次向量请求使用独立 30 秒截止时间，四轮都超过 10 秒。

## 改动与因果边界

唯一生产改动在 `VectorIndex.search`：

```python
# A：每篇文档在 Python 中调用一次标量 isfinite
candidates = [index for index in range(scores.shape[0]) if np.isfinite(scores[index])]
# B：批量生成相同顺序的 Python int 候选列表
candidates = np.flatnonzero(np.isfinite(scores)).tolist()
```

矩阵打分、heapq top-k、过滤、分数并列时 item_id 排序、模型与检索深度均未改变。原始 `labels.csv` 未改。A 与 B 均包含此前的编码器初始化锁；因此不会把初始化锁的影响记在这一行扫描改动上。

四个服务各从冻结的 src 快照导入，服务日志记录实际 import_origin 和 PID。完整源码文件哈希清单比较确认：A 两轮一致，B 两轮一致，A/B 仅 `searchpilot/search/vector_index.py` 不同。该文件 SHA-256：

- A：`c12e5c0f1f061e62438023555de7cb6fc4cfb7901a2f6ae58a3f585a1e04f6bb`
- B：`bc774bb92b928a08a2c905a6b3de45c2ec497fc8d391345bd961a72902f9f8ea`
- 四轮压测脚本一致：`fc4fe4c38d8d8f3326a089e1e724e8bcfe3c3a4093f9ee33643e1bf26e9198a2`

运行时 checkout 的 commit 为 `edf203a1cbafaeab1976d86833fa8cae82eb7e25`，dirty=true；以上冻结源码哈希才是实际服务器版本依据，不将客户端工作区状态冒充服务版本。

- `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 均未设置；`TOKENIZERS_PARALLELISM=false`。没有同时改变线程配置。

实际隔离工厂为：

```python

```

它复用生产 `/search` 路由、真实索引、真实缓存 BGE 和 LTR，未注入数据库、推荐、feedback、CTR。每轮初始及恢复时，search/vector_index/ltr 检查为 true；recommend/feedback 为 false，**全局 `/health/ready` 为 503**，恢复 `/health/live` 为 200。只满足本轮搜索测量前提，不构成整站就绪或恢复验收。

每轮实际完整命令数组保存在 [机器可读证据](performance-2026-10-14-evidence.json) 的 `rounds[].command_argv`。统一压测参数为：

复现 A/B 还须按原协调脚本分别设置冻结 src 的 PYTHONPATH、清空数据库/令牌配置、启用离线缓存并使用上述隔离工厂。不能把单独这条客户端命令当作完整复现。已有输出不可覆盖；每轮使用新目录。原协调脚本、源码差异和请求记录随原始证据包保留。

## 每版本两轮合并

每个版本每模式保留 **240/240** 请求。分位数从合并后的逐请求延迟重新排序，使用 `ceil(q*n)-1` 的 nearest rank，**不是两轮分位数取平均**。吞吐为总成功数除以两个正式段时长之和。

| 模式 | 版本 | 成功/全部 | p50 ms | p95 ms | p99 ms | 最大 ms | 成功 req/s |
|---|---|---:|---:|---:|---:|---:|---:|
| bm25 | A | 240/240 | 32.792 | 80.712 | 100.788 | 104.306 | 104.115 |
| bm25 | B | 240/240 | 44.169 | 86.782 | 132.145 | 134.626 | 81.095 |
| vector | A | 240/240 | 730.812 | 1036.228 | 1338.708 | 1393.383 | 5.451 |
| vector | B | 240/240 | 349.084 | 539.973 | 1499.645 | 1640.744 | 11.026 |
| hybrid | A | 240/240 | 698.992 | 948.051 | 1112.690 | 1138.353 | 5.788 |
| hybrid | B | 240/240 | 408.754 | 536.392 | 640.391 | 702.243 | 9.985 |
| ltr | A | 240/240 | 961.701 | 1359.050 | 1487.010 | 1615.661 | 4.218 |
| ltr | B | 240/240 | 816.641 | 1016.421 | 1960.829 | 2437.557 | 4.773 |

vector / hybrid / LTR 吞吐分别上升 102.26% / 72.51% / 13.14%。但是 B-search-2 的 vector p99=1619.611 ms、LTR p99=2346.090 ms，均高于两轮 A。合并后 vector/LTR p99 仍退化，不能用 p95 改善掩盖它们。

未修改的 BM25 控制组也明显波动：p95 在四轮间为 49.495–102.362 ms，合并 B 比 A 高 7.52%，吞吐低 22.11%。这提示短轮次存在环境或调度噪声；本轮没有足够证据把具体尾部抖动归因于 GIL、BLAS、CPU 频率或后台任务，也不对这些变化做统计显著性声明。仅两轮/版本不能证明稳定容量或长期收益。

## 服务资源采样与恢复

协调器每 0.5 秒采样实际服务器进程，表中严格筛选 `measured_start_epoch..measured_end_epoch` 内记录。窗口覆盖正式客户端进程，包括 16 次预热和启动开销，排除独立首次向量请求及恢复阶段；不是纯粹的 480 请求服务 CPU 时间。

CPU 平均核数=`(末样本累计CPU秒−首样本累计CPU秒)/(末样本时间−首样本时间)`。除以 12 后得到占本机逻辑 CPU 总量百分比。工作集使用窗口内观察到的最大值，**约 0.5 秒采样无法捕捉所有瞬时峰值**；未使用进程生命周期 PeakWorkingSet 代替窗口峰值。

| 轮次 | 实际 PID | 样本数 | 首末采样间隔 s | CPU 增量 s | 平均核数 | 占12逻辑CPU | 采样工作集最大 MiB |
|---|---:|---:|---:|---:|---:|---:|---:|
| A-search-1 | 25300 | 147 | 74.481 | 539.000 | 7.237 | 60.31% | 1049.664 |

候选两轮观察到更低的 CPU 增量，但资源表包含预热/客户端启动窗口，不能直接换算成单条查询纯服务成本。内存采样差异很小，不据此宣称显著内存改善。

四轮结束时 live=200；ready=503 且搜索相关 checks 保持 true。四个自建进程均 graceful 退出、退出码 0。未做服务强制取消完成或残留任务审计，这些健康探测不能替代该证明。

## 先前启动失败与证据

在 ABBA 搜索轮次之前，先尝试了两次默认应用启动，均未发出搜索请求：

1. `A1`：90 秒内未达到就绪，最终强制关闭。该轮资源采样错误指向 Windows launcher PID，**资源数据无效，未纳入任何汇总**。

随后明确缩小工厂到 search-only 才执行上述四轮。原始 `A1`、`A1-retry` 的 coordinator 和日志完整保留，不把它们从项目已知限制中删掉。
